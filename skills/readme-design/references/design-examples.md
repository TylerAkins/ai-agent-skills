# README Design Examples

Consult these when choosing a visual direction or improving a weak reader path.
Reviewed October 31, 2026. These are examples, not templates or proof that a layout
improves adoption. Inspect the current source and render before borrowing a pattern;
commands, branding, claims, and installation choices belong to their own projects.

| Example | Pattern to study | Apply selectively |
| --- | --- | --- |
| [uv](https://github.com/astral-sh/uv#readme) | A recognizable opening, concise positioning, an early visual comparison, installation, and links to focused documentation. | Use an early visual when it explains a verified benefit; do not invent benchmark claims or copy its section inventory. |
| [bat](https://github.com/sharkdp/bat#readme) | Screenshots paired with specific capabilities make a command-line tool understandable before installation. | Show a representative result when appearance matters; avoid a screenshot for every minor feature. |
| [fzf](https://github.com/junegunn/fzf#readme) | Demonstrations, navigation, and labeled installation alternatives support a tool with several entry paths. | Keep alternatives discoverable and complete; do not copy the full length of a mature project's reference material. |

Choose the pattern that serves the actual audience. A small library may need only
a compact code example; a visual application may need one strong screenshot.
Check asset contrast, descriptive links, useful alt text, and layout on narrow
screens. Borrow principles rather than another project's identity or prose.
